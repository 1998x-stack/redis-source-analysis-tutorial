Chapter 05 / Redis Source Anatomy

从 ziplist 到 listpack：Redis 紧凑容器的取舍

比较双向链表、ziplist 的连锁更新、listpack 的 backlen 和 Redis 7.2 List 的编码选择。

源代码基准 Redis 7.2.4 · 原理 → 图解 → 调用路径 → 实验 → 边界

链表和紧凑数组为何会并存？

一个包含几十个小字符串的 Redis List，需要快速在头尾插入，也不希望每个元素额外背着两个指针和独立分配成本。双向链表天然支持已知节点的 O(1) 连接与删除，却牺牲局部性；一整块连续字节数组能减少指针与分配开销，但在中间插入通常需要搬移后续数据。

Redis 的演进不是“某种结构全面消灭另一种”：adlist 仍是通用内部链表；ziplist 是有历史意义的紧凑布局；listpack 改变元素长度编码以避免一种严重连锁更新；quicklist 则把连续内存划分成可管理的结点。用户可见的 List 数据类型又处于这些容器的上层。

ziplist 的 prevlen 为什么可能连锁扩容？

在 ziplist 中，每个 entry 保存前一个 entry 的字节长度。如果“前一个 entry”变大到跨过长度编码阈值，后一个 entry 的 prevlen 可能从 1 字节扩展为 5 字节；这个 entry 自身因此变大，可能再导致再下一个 entry 扩展。这是特殊构造下的级联更新风险，不是每次插入都会发生。

在 Redis 源码中，ziplist 的相关阈值是 ZIP_BIG_PREVLEN（254 字节），因此不能含糊地说“每个节点始终记录固定大小长度”。更重要的是，ziplist 已不应被描述成 Redis 7.2 全部 List 值的唯一当前编码。

listpack：把反向长度放在每个 entry 的尾部

Redis 7.2.4 的 listpack 具有 6 字节全局头部：total_bytes（4 字节）和 num_elements（2 字节），末尾使用 0xFF 作为结束标志。每个 entry 包含数据编码、载荷和尾随 backlen。backlen 对应自身 entry 正向部分的长度，用变长编码存放，反向遍历时可根据它回退到 entry 起点。

这消除了 ziplist 使用“下一条存前一条长度”而触发的级联长度字段更新问题。不过，listpack 并没有让连续数组的中间插入变成 O(1)：扩容、字节移动和内存分配仍然存在。应把“避免一种级联机制”和“所有操作性能恒定”严格分开。

// 教学用字节结构示意，不是可直接解码的合法 listpack:
[total_bytes:4][num_elements:2]
[encoding + payload][backlen(entry0)]
[encoding + payload][backlen(entry1)]
...
[0xFF]  // end marker

编码字段会按字符串大小或整数范围采用不同形式，backlen 的编码长度也依 entry 的大小变化。不要把图中的 backlen 当成某个固定的 1 字节指针。

Redis 7.2：List 既可能是 listpack，也可能是 quicklist

Redis 7.2 的 src/t_list.c 包含编码转换逻辑。对小型列表，直接存一整块 listpack 有机会免去链表节点头开销；当增长超过限制，可能转换成 quicklist。quicklist 由链式结点组织，常用结点内部是 listpack；对特定较大元素存在 PLAIN 结点形式。list-max-listpack-size 控制分段策略，具体行为需要以版本和配置核对。

这使得两个直觉可以同时成立：局部紧凑降低缓存和分配开销，分段组织降低长数组反复移动的范围。代价是实现变得更复杂，需要维护节点计数、压缩状态、迭代位置和转换阈值。

adlist 并没有消失：通用链表与用户 List 的区别

src/adlist.h 定义 listNode（prev、next、value）和 list（head、tail、len 等），用于通用容器场景。不要将它与 Redis 对外 List 类型直接画等号：在 7.2.4 中，用户 List 的底层可能是 listpack 或 quicklist，通用 adlist 则可被服务器内部其他子系统使用。

表示随机访问头尾变更内存局部性 / 代价
adlist需要遍历，通常 O(n)已知边界时 O(1)节点单独分配，指针成本较高
ziplist通常按 entry 线性移动可能搬移字节并级联更新连续内存，但 prevlen 有特定级联风险
listpack按 entry 迭代，通常 O(n)可能内存搬移 / 扩容紧凑，backlen 为后向遍历服务
quicklist需定位结点及内部偏移兼顾端点与分段连续性结点管理、压缩和编码转换复杂

在真实 Redis 中观察编码变化

./src/redis-server --bind 127.0.0.1 --port 6390 --save "" --appendonly no
./src/redis-cli -p 6390 LPUSH tiny:queue a b c
./src/redis-cli -p 6390 LRANGE tiny:queue 0 -1
./src/redis-cli -p 6390 OBJECT ENCODING tiny:queue
./src/redis-cli -p 6390 CONFIG GET list-max-listpack-size
./src/redis-cli -p 6390 SHUTDOWN NOSAVE

LPUSH 连续插入 a、b、c 后，LRANGE 的顺序应为 c、b、a。对这类小列表，7.2.4 可能报告 listpack；不要假设任何配置或数据规模都会返回该编码。通过改变规模并观察 OBJECT ENCODING，你可以理解“用户类型不变，内部表示改变”的真正含义。

交互用于追踪概念路径，不替代对实际二进制文件的单步验证。

用两个问题判断使用哪一层抽象

当你调试 LPUSH 时，先问：“这个 Redis List 当前是什么对象编码？”这决定你应进入 t_list.c 的哪条分支。再问：“该编码内部的字节如何定位、移动和回收？”这才把视线转向 listpack、quicklist 和必要时的 adlist。

也不要把 ziplist 画成 7.2 当前默认的数据结构。ziplist 仍然值得学习，是因为它揭示了长度编码如何产生连锁副作用。读源码的价值不仅在于记住当前算法，更在于能用明确的不变量判断一次结构设计的代价。
