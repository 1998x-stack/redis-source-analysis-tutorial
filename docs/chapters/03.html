zmalloc 与 jemalloc：从申请字节到内存统计

拆开 Redis 的分配包装层、可用块大小、编译期前缀分支，以及 used_memory 与 RSS 的测量差异。

源代码基准 Redis 7.2.4 · 原理 → 图解 → 调用路径 → 实验 → 边界

Redis 实际想统计哪种“内存”？

Redis 的键值可以由 SDS、字典、quicklist 等不同数据结构组成，但低层的内存分配一般最终走向 zmalloc 包装层。包装层提供统一接口并维护已分配内存的统计，底层则可以选择不同 allocator，例如 Linux 上常见的 jemalloc 或显式设置的 libc。

把 zmalloc 想成一个“每次申请前都插入 8 字节头”的函数会导致错误的内存诊断。Redis 7.2 的 zmalloc.c 明确区分了分配器能否报告可用块大小的两条互斥编译路径。认识这个分支，比背几条 jemalloc 性能宣传更重要。

一张分支图，看清 PREFIX_SIZE

源码中的关键判断近似如下（只截取分支，不把伪码当完整分配实现）：

#ifdef HAVE_MALLOC_SIZE
# define PREFIX_SIZE 0
#else
# define PREFIX_SIZE sizeof(size_t) /* 部分平台为对齐取 8 */
#endif

/* HAVE_MALLOC_SIZE: 直接查询可用大小、累计 used_memory
 * 否则：把 requested size 写在分配块前，返回偏移后的指针 */

支持可用大小接口的路径使用 zmalloc_size(ptr) 获取 allocator 实际可用块大小；不支持的路径才把 size 写入额外前缀。无论哪条路径，都应通过匹配的接口释放，不能拿用户指针直接传给错误的 free 实现。Redis 还暴露 ztrymalloc 类接口让调用者处理失败，并提供默认终止进程的 OOM handler。

交互用于追踪概念路径，不替代对实际二进制文件的单步验证。

used_memory、allocator 与 RSS 不是同一张账

指标通常反映什么最常见误解
used_memoryRedis allocator 口径的已分配大小等于内存中所有键值数据净大小
used_memory_rss进程实际常驻物理页的近似口径100% 都是 Redis 业务对象
used_memory_peak观察窗口内曾达到的峰值当前每个对象都曾达到峰值
mem_fragmentation_ratioRSS 与 allocator 统计关系的粗略信号单个指标就能证明 jemalloc 外部碎片

空闲页未立即归还、fork 子进程、不同分配级别、共享页和系统映射都可能影响观察结果。遇到 RSS 高，不要只盯一个比率：应结合 INFO memory、MEMORY STATS、进程监控和当时的工作负载进行判断。

小对象为什么不等于请求大小？

如果你请求 33 字节，实际分配器可能按 size class 提供更大可用空间。Redis 7.2 的 zmalloc_usable() 允许调用方获取可用大小并复用这些空间；这与 SDS 扩容后的 alloc 字段紧密相关。用户对象、allocator 的元数据、分配器保留页以及系统 RSS 并非简单逐级包含的三个整数。

jemalloc 通常通过 arenas / bins / thread cache 管理不同尺寸的对象。它可以改善某些分配场景，但不能保证所有工作负载零碎片，也不能把它说成“每次分配都无锁”。编译选择和运行平台必须写进任何比较。

在源码追踪时，先搜索 zmalloc_usable 和 HAVE_MALLOC_SIZE，再追 used_memory 的增减。这样能解释为什么两台机器上“相同 Redis 命令”可能有不同的内存占用。

可重复实验：对照内存曲线

独立临时实例中用同一条键操作观察内存统计，避免把服务器启动本身的初始化开销误认为业务对象开销。以下示例不会把统计差值解释为单个 SDS 的精确物理大小。

./src/redis-server --bind 127.0.0.1 --port 6390 --save "" --appendonly no
# 另一终端记录基线
./src/redis-cli -p 6390 INFO memory
./src/redis-cli -p 6390 MEMORY STATS
# 写入多个不同的键；重复实验需 FLUSHDB 并留意 allocator 缓存
for n in $(seq 1 100); do
  ./src/redis-cli -p 6390 SET "mem:$n" "sample" >/dev/null
done
./src/redis-cli -p 6390 INFO memory
./src/redis-cli -p 6390 MEMORY USAGE mem:1
./src/redis-cli -p 6390 SHUTDOWN NOSAVE

观察点：used_memory 与 used_memory_rss 的增量可能不同；MEMORY USAGE 估计单个键的使用情况，也不能直接与整个进程 RSS 做精确守恒。若想比较 jemalloc/libc，必须在同一平台上分别干净重建并记录样本；这份教程不凭空给出吞吐提升百分比。

常见误区与排查顺序

误区一：“zmalloc 必定多占 sizeof(size_t)”。不对，先看编译宏。误区二：“used_memory 是机器上 Redis 的真实全部占用”。不对，还要看操作系统驻留页。误区三：“jemalloc 的 arena 数量越多越好”。不对，空间开销和并发行为取决于负载。误区四：“删除键后 RSS 必须立即等比例下降”。不对，allocator 可保留页用于未来分配。

下一步建议打开 src/zmalloc.c，将这里的两个分支分别画出来，再沿着 sdsnewlen() 跟踪一次小字符串分配。这样就可以把抽象统计和真实对象布局连接起来。
