两个表面相近的集合：Set 和 Sorted Set 要解决不同问题

假设一个活动系统需要维护用户是否领取优惠券：SISMEMBER claimed user:42 应回答成员是否存在，不关心顺序。排行榜则必须在查询某人的分数之外，快速取出若干连续名次和分数范围。这两种请求看起来都叫“集合”，但约束不同：Set 关心唯一性与无序成员检查，Sorted Set（ZSET）还必须维护全序。

Redis 的实现并不把某种容器写死到所有集合：在 7.2.4，Set 能用 intset、listpack 或 hashtable；ZSET 可以使用紧凑的 listpack，在转换到 skiplist 编码后同时维护成员字典和有序跳表。读命令源码前应确认 OBJECT ENCODING 返回的当前编码。

关键区分：SET 是写 String 键的命令；Set 才是集合逻辑类型。ZADD 是有序集合成员写入命令，和普通 String 的 SET 完全不是同一路径。

SADD 真实调用路径：首先保证唯一性

在 t_set.c 中，saddCommand() 查找或创建对象，再逐项调用集合添加函数。setTypeCreate() 能依据输入值是否可表示为整数、以及 size_hint 决定新集合使用何种编码；setTypeAddAux() 则按当前编码将成员写入，同时避免重复。

当前编码定位成员的方法插入时的代价
intset已排序整数，二分查询可能移动整块数组；升级宽度会重写已有成员
listpack紧凑 entry 顺序查找可节省小集合内存，但中间插入/查重涉及线性扫描
hashtable哈希桶及碰撞处理平均常见查找很快；需额外桶/entry 内存

例如 SADD 含一个已经存在的成员时，该成员不会被重复存储，命令返回值只计算真正新增的数量。将输入由整数变成普通字符串时，7.2.4 的小 Set 不一定立刻转换为 HT：在符合配置和容量安全要求时，还可能选择 listpack。这是旧教程中容易遗漏的分支。

SINTER、SUNION、SDIFF：算法依赖候选集规模

考虑三个集合 A={a,b,c}、B={b,c,d,e,f,g}、C={a,b,c,h,i}。交集 A∩B∩C={b,c}。如果先扫描最大集合 B，并逐项检查其他集合，会浪费大量候选；Redis 在 sinterGenericCommand 里按集合的基数选择较小集合做驱动集合，成员查找则取决于集合编码。

集合算法的复杂度不是一个脱离输入大小的固定 O(1)。粗略地，交集通常受最小候选数与各集合成员判断成本影响；并集需要枚举输入并去重；差集可能选择不同的实现策略以降低工作量。SINTERSTORE 和 SUNIONSTORE 还需要构建新的结果键；把源键的基数当成输出基数也不正确。

模型显示可解释的概念分支，不执行真实 Redis 命令。

ZADD 是一次有条件的索引更新，不是简单插入跳表

zaddGenericCommand() 解析分数、成员以及 NX/XX/GT/LT、CH、INCR 等标志，再调用 zsetAdd()。当前是 listpack 则在紧凑编码上查找或更新；当前是 SKIPLIST 则通过字典判定成员是否存在，再维持跳表的排序不变量。若新写入跨越紧凑编码阈值，需要转换表示，这一操作可能比单次成员查找重得多。

条件的准确含义：NX 仅添加新成员；XX 只更新已有成员；GT/LT 限制更新分数方向；CH 让返回整数包含新加或分数发生变化的已有成员；INCR 使操作变成增量计分，其返回值不是新增计数。也不能断言 ZADD 每次更新都改变排名，分数未变或不满足条件时无需迁移跳表节点。

/* 教学用分支概览：不是完整 Redis 函数 */
zaddGenericCommand(c):
    parse options and score/member pairs
    check incompatible flags and score validity
    for each item:
        zsetAdd(zobj, score, member, flags, ...)
           if current encoding == LISTPACK: update compact representation
           if current encoding == SKIPLIST: coordinate dict and zsl
    reply according to flags / actual updates

跳表的随机层高只影响其索引形状，并不会随机改变 ZRANGE 的排序结果。排序先按分数，再按成员字节序，稳定地决定有序结果。

ZRANGE 与 ZRANK：范围查询并非免费

zrangeGenericCommand() 综合索引/分数/字典序范围和反序等参数，底层根据 ZSET 当前表示选择迭代方式。ZRANGE k 0 9 WITHSCORES 需要寻找起点并逐个输出元素；输出 100 万个成员就必须付出相应扫描和网络传输代价，因此不能把“有序查询 O(log n)”理解为“任意大的范围输出 O(log n)”。

在 SKIPLIST 表示下，zslGetRank() 内部使用 1-based 索引，而客户端 ZRANK 返回 0-based 排名。区间查询还受起点查找成本和返回元素数控制。使用 WITHSCORES 要返回额外数据，远程客户端测量可能主要受输出缓冲和网络吞吐影响。

命令读取的逻辑注意点
ZSCORE定位成员并返回分数dict vs listpack 编码分支
ZRANK按 score/member 顺序定位秩客户端排名从 0 开始
ZRANGE定位起点并逐个生成区间回复输出 M 个成员至少需 O(M) 处理
ZCOUNT统计分数区间内成员数依据编码与范围定位路径

最小实验：验证唯一性、集合运算和 ZADD 条件

仅在本地隔离的 Redis 7.2.4 实例中执行；第 2 章有固定版本构建方法。本实验不对随机内部跳表高度作断言，只检验客户端可观察的正确行为。

./src/redis-server --bind 127.0.0.1 --port 6390 --save "" --appendonly no
./src/redis-cli -p 6390 DEL a b rank
./src/redis-cli -p 6390 SADD a apple banana apple
./src/redis-cli -p 6390 SADD b banana cherry
./src/redis-cli -p 6390 SINTER a b
./src/redis-cli -p 6390 OBJECT ENCODING a
./src/redis-cli -p 6390 ZADD rank 10 alice 20 bob
./src/redis-cli -p 6390 ZADD rank NX 99 alice
./src/redis-cli -p 6390 ZADD rank XX CH 30 bob
./src/redis-cli -p 6390 ZRANGE rank 0 -1 WITHSCORES
./src/redis-cli -p 6390 SHUTDOWN NOSAVE

预期：首次 SADD 只计算 apple 与 banana 两个不同成员，返回 2；SINTER 返回 banana；ZADD NX 尝试更新已有 alice 时返回 0，随后 XX CH 更新 bob 则返回 1。最终排序是 alice/10、bob/30。OBJECT ENCODING a 在小集合下可能返回 listpack，并不意味着 SADD 没有查重。

复杂度与版本边界：把算法说法落回实现

当 Set 还是 listpack 时，成员检查并不享受哈希表平均 O(1) 查询；当 ZSET 还是 listpack 时，命令也不必调用跳表。对 SINTER、ZRANGE 的性能分析必须同时说明 n、k（涉及的集合数）、m（输出数量）与当前对象编码。Redis 7.2.4 具备这些编码分支，但配置阈值可能变化，本文不将默认值误写成硬性存储规律。
