Chapter 01 / Redis Source Anatomy

Redis 源码全景图：一条命令穿过了什么？

以 SET 请求为线索，建立网络、协议、命令、对象、数据库和持久化之间的完整因果图。

源代码基准 Redis 7.2.4 · 原理 → 图解 → 调用路径 → 实验 → 边界

一次 SET 到底改变了哪些东西？

设想客户端发送 SET visitor:42 active。直觉上它只是向一个哈希表写入键值对，但源码中的路径远不止写入一个指针：网络层要读到完整的 RESP 帧，解析参数成为 redisObject，执行层要查找命令、检查条件，数据库层才能插入或替换键值。执行后回复还须排队写回套接字。若启用了持久化或复制，写操作还涉及传播。

不要把“命令执行在主线程”理解为 Redis 所有工作都由一个线程完成。Redis 7.2 的主命令执行路径由事件循环驱动，但后台持久化子进程、I/O 线程、惰性释放任务可以存在；它们和主线程的职责不同。

读源码的起点不是记住文件目录，而是先回答四个问题：请求在哪里形成 argv？什么地方真正调用命令函数？对象在哪里落入字典？成功回复由谁排队发送？

第一张图：从 RESP 到命令调用

沿着 src/networking.c 读 readQueryFromClient()，会遇到 processInputBuffer()。协议解析将输入构造为客户端的 argv。再进入 src/server.c 的 processCommand()，检查命令权限、参数与执行条件，最终由 call() 分派到命令的 proc。

阶段看哪些函数 / 状态不能误解成
网络读readQueryFromClient、querybuf一个 read 必然恰好是一条完整命令
协议解析processInputBuffer、argc/argv先执行再解析
命令分派processCommand、call所有命令都绕过 ACL 和事务检查
输出addReply*、可写事件addReply 调用就是同步发送完成

在 I/O 层，TCP 是字节流。单次读可能只取到半个命令，也可能含多条命令。理解这个事实，才能看懂为什么 Redis 需要输入缓冲区和状态机。

这里不列出所有文件，只保留驱动下一步理解所需的最小集合。尤其不能把数据结构代码和 Redis 命令入口混成同一层：sds.c 可以处理二进制字符串，但不会决定 SET 的 NX/XX 语义。

把图上的每根箭头对应到代码

阅读时可以用“教学伪代码”整理控制流，再回到固定版本的实现核对细节。下面是逻辑位置，不是逐行复制的 Redis 函数实现：

// 教学级逻辑流程：不要直接编译这段伪代码
onReadable(client):
    appendSocketBytes(client.querybuf)
    while (thereIsACompleteRESPCommand):
        client.argv = parseRESP(client.querybuf)
        processCommand(client)    // 参数、ACL、事务等检查
            call(client)          // c->cmd->proc(c)
                setCommand(client)
                    setGenericCommand(...)
        queueReply(client)         // 之后由网络层负责发送

真实 call() 除了运行命令函数，还包裹统计、慢日志、传播等前后处理，processCommand() 可能提前拒绝命令或令客户端进入阻塞状态。看调用栈时要分辨“命令函数做的事”和“执行包装层做的事”。

从 argv 到内存：两个不同的字符串层

同一条 SET 中，命令参数被表示为 Redis 对象；redisObject 持有类型与编码，实际字节可能由 SDS 保存。数据库 key 和 value 又处于键空间字典的不同角色。可把这一链看作：输入字节 → 参数对象 → 对象编码 → SDS / 整数 / 容器 → 数据库字典。

“SET 一定分配一个新的 SDS”不是普遍成立的描述：整数值可能采用整数编码，已有对象可能被复用或替换，且分配器的内部布局不等于 Redis 对象布局。关于 SDS 头部与对象编码，我们在第 4 章单独拆解。

交互用于追踪概念路径，不替代对实际二进制文件的单步验证。

最小实验：看到命令和对象编码

从官方 Redis 7.2.4 源码编译后，在临时端口启动隔离实例，避免改动本机生产 Redis。以下命令适用于类 Unix shell；第 2 章提供调试编译方法。

./src/redis-server --port 6390 --save "" --appendonly no
# 在另一个终端：
./src/redis-cli -p 6390 PING
./src/redis-cli -p 6390 SET visitor:42 active
./src/redis-cli -p 6390 GET visitor:42
./src/redis-cli -p 6390 TYPE visitor:42
./src/redis-cli -p 6390 OBJECT ENCODING visitor:42
# 实验结束（仅关闭这个临时端口实例）：
./src/redis-cli -p 6390 SHUTDOWN NOSAVE

预期：PING 返回 PONG，SET 返回 OK，GET 返回 active，TYPE 返回 string。OBJECT ENCODING 显示内部对象编码，不是 SDS 头部类型，也不是“是否持久化”。

示例的 --save "" 和 --appendonly no 只用于临时、无持久化实验。不要将此命令作为生产部署模板。

边界：事件循环不是“所有操作都不阻塞”

主线程执行高耗时命令仍可能阻塞其他客户端的进展。某些命令在执行中会触发复制、过期、通知等副作用。Redis 7.2 和后续 8.x 的实现、构建与模块集合也有差别，所以不能引用某个最新分支的函数签名来断言 7.2.4 的行为。

建议回看三件事：readQueryFromClient 负责哪类字节？processCommand 和 call 的边界在哪？redisObject 与 sds 为什么不是一个东西？回答清楚后，再去调试真实二进制。
